# ApplyHub 데이터 처리 효율 검토

검토일: 2026-09-19

> 아래 내용은 수정 전 분석 기록이다. 실제 적용 내역, 검증 결과와 남은 제약은 [DATA_PROCESSING_CHANGES.md](DATA_PROCESSING_CHANGES.md)를 참조한다.

## 범위와 결론

DB 스키마·연결 풀, HTTP 요청/응답, 접수·회원·서류·수험표 서비스, 백업/복원, 첨부파일, 관리자 초기 로딩·그리드·다운로드 경로를 검토했다. 가장 먼저 수정할 부분은 **수험번호 생성과 접수 저장의 연결 사용**, 다음은 **전체 데이터 중복 조회와 서버 페이지 처리**다.

최초 분석 시점에는 애플리케이션 코드를 수정하지 않았으며, 이후 사용자 요청에 따라 개선 사항을 적용했다. 운영 DB에 접속하거나 서버를 실행하지 않았으며, 운영 데이터 규모·실행 계획·실제 응답시간은 측정하지 않았다. 아래 수치는 실제 서비스 함수에 가상 데이터를 공급하거나 원본 함수를 추출해 외부 의존성을 대체한 검증 결과다. 운영 부하 테스트 결과로 해석하면 안 된다.

## 1. 수험번호 생성: 누적 데이터에 비례하는 반복 조회

근거: `server/modules/applications/service.js:3809`, 특히 `3833–3845`; `db/schema.sql`의 `app_meta`; `server/modules/bootstrap/schema/applications.js:23`.

`generateApplicantExamineeNo()`는 매번 `sequenceStart`에서 시작해 후보 번호마다 `SELECT ... WHERE examinee_no = ?`를 수행한다. 기존 번호가 같은 규칙 아래 연속으로 사용 중이면 다음 발급의 DB 왕복 수가 계속 증가한다. 인덱스가 있어도 왕복 횟수 자체는 줄어들지 않는다.

- 기존 번호 1~10,000이 점유된 가상 DB를 연결한 원본 함수 검증: 다음 번호 10,001 발급에 SELECT 10,001회.
- 같은 번호 그룹에서 1번부터 N명까지 순서대로 발급하면 후보 확인은 합계 N(N+1)/2회. N=10,000이면 50,005,000회다. 삭제 공백·번호 그룹 분산에 따라 실제 횟수는 달라진다.
- 서로 다른 접수의 일반 SELECT가 같은 빈 번호를 볼 수 있다. 현재 `examinee_no`는 일반 인덱스이며 UNIQUE가 아니다. 회원별 잠금은 다른 회원 사이의 번호 발급을 보호하지 않는다. 두 호출에 같은 빈 스냅샷을 제공한 검증에서는 둘 다 `1`을 반환했다. 실제 DB 동시 접수 충돌은 별도 통합 검증이 필요하다.

수정 제안:

1. 번호 규칙의 충돌 범위를 기준으로 카운터 테이블을 만든다. 날짜·전형 코드 등이 실제 번호에 반영되는 방식을 고려해 카운터 키를 정한다.
2. 같은 트랜잭션/연결에서 카운터 행을 원자적으로 증가시키거나 `SELECT ... FOR UPDATE` 후 증가시킨다. 최초 카운터 생성 경쟁도 처리한다.
3. 기존 중복·빈 문자열을 먼저 조사하고 정리한 후 `app_meta.examinee_no`에 UNIQUE를 적용한다. 미발급은 NULL로 통일한다. 중복 자료는 자동 삭제하지 않는다.
4. 기존 번호를 기준으로 카운터를 초기화하고, 자릿수 초과·규칙 변경·중복 키 재시도 정책을 검증한다. 삭제된 번호의 재사용 필요 여부는 별도 정책으로 결정한다.

번호 카운터의 잠금 사용은 [MySQL 공식 locking reads 문서](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)에 설명된 방식과 같다. 목표는 발급당 번호 할당 SQL을 기존 접수 건수와 무관한 고정 개수로 줄이는 것이다.

## 2. 접수 저장 중 연결 풀 재진입

근거: `db.js:10`, `server/modules/applications/service.js:1519`, `4226`, `4302`, `4340`.

`saveApplicantSubmission()`은 풀에서 연결을 빌려 트랜잭션을 시작한 뒤, `getApplicantSettings()`를 호출한다. 이 함수는 빌려 둔 `connection` 대신 전역 `query()`를 사용하므로 풀에서 다른 연결이 필요하다.

연결 풀이 모두 이런 요청에 점유되면 각 요청이 연결을 보유한 채 추가 연결을 기다릴 수 있다. 기본 풀 크기는 10이다. 원본 저장/설정 조회 함수를 추출해 단일 연결 풀을 모사한 검증에서는 첫 연결이 반환되지 않은 상태로 설정 조회가 추가 연결을 기다리는 경로를 확인했다. 이는 실제 MySQL 실행 검증은 아니며, DB 행 잠금 교착과 별개인 애플리케이션 연결 대기 문제다. 운영 환경에서의 발생 빈도는 측정하지 않았다.

수정 제안:

- `getApplicantSettings({ queryable })`처럼 실행 연결을 주입하고 트랜잭션 안에서는 항상 동일한 연결을 사용한다. 설정의 시점 일관성이 필요 없다면 트랜잭션 시작 전에 읽을 수도 있다.
- 다른 트랜잭션 함수도 같은 패턴으로 감사한다. 풀 크기 확대만으로 해결하려 하지 않는다.
- 현재 커밋 이후 사진/파일 저장을 기다리는 동안에도 연결을 보유한다. DB 작업 완료 시 연결을 반환하도록 구조를 분리한다.
- 파일 저장은 임시 파일 준비 → 짧은 DB 작업 → 파일 확정/실패 복구 방식으로 설계한다. 현재 접수 저장은 DB 커밋 뒤 파일을 쓰므로 파일 실패 시 DB만 남을 수 있고, 서류 저장은 트랜잭션 중 파일을 쓰므로 잠금 시간이 길어진다. 단순히 파일 쓰기 순서만 이동하지 말고 실패 시 정합성을 함께 다룬다.

검증 목표: 풀 크기 1·2·10과 풀 크기를 넘는 동시 접수에서 모두 완료되는지 확인하고, 파일 저장 실패도 주입한다.

## 3. 초기 로딩에서 전체 접수 조회 3회와 전체 재로딩

근거: `server/modules/system/service/summary.js:36`, `server/modules/admit-cards/submission-records.js:6`, `38`, `server/modules/applications/service.js:3083`, `client/app/bootstrap-loader.js:52`.

호출 구조:

```text
getBootstrapPayload()
  ├─ getApplicantSubmissions()                 → 전체 접수 조회
  ├─ getExaminees() → getApplicantSubmissions() → 전체 접수 조회
  └─ getPrintHistory()
       ├─ 전체 print_log 조회
       └─ getExaminees() → getApplicantSubmissions() → 전체 접수 조회
```

실제 summary/ticket 서비스에 가상 접수 1,000건을 공급한 결과, 접수 조회 3회와 수험표 레코드 변환 2,000회를 확인했다. 출력 이력이 없어도 이 경로는 전체 접수를 읽는다.

전체 접수 조회는 모든 답변 행과 조인/집계를 포함한다. 기본정보와 전체 답변을 함께 전송하며, `answerItems`와 `answerMap`에 답변 값도 중복으로 실린다. 초기 로딩에는 모든 출력 이력과 양식 HTML도 포함된다. 사진 한 장 변경 후에도 `loadBootstrapData()`를 다시 호출한다(`client/features/applications/admin-submissions-workflow.js:108`). 출력 기록 후에도 전체 재조회가 있다(`client/features/admit-cards/workflow/print-history.js:43`).

수정 제안:

- 단기: 요청 하나 안에서 접수를 1회만 읽고 수험표/출력이력 변환에 공유한다. 개인 데이터 전체를 전역 캐시에 넣을 필요는 없다.
- 본 수정: bootstrap은 화면 기본 설정과 작은 요약으로 축소하고, 접수 목록·출력 이력·양식 본문은 해당 화면/API에서 조회한다.
- 목록 응답은 기본정보와 상태만 전달하고 전체 답변은 상세 조회로 옮긴다. `answerItems`/`answerMap` 중 하나만 전송하고 필요하면 클라이언트에서 변환한다.
- 사진 교체·출력 기록·설정 변경 후에는 관련 행/요약만 갱신한다.
- 대시보드의 수치도 브라우저 전체 접수 배열 대신 서버 집계 API로 제공한다(`client/features/dashboard/data.js`).

요청 내 재사용으로 전체 조회 횟수를 3→1로 줄일 수 있지만, 이것만으로 전체 데이터 로딩 문제까지 해결되는 것은 아니다.

## 4. 서류 관리의 페이지 처리가 전체 조회 뒤에 있음

근거: `server/modules/applications/document-status.js:28`, `server/modules/applications/service.js:4518`, `client/features/applications/document-management.js`.

현재 `list()`는 전체 접수를 불러와 필터 선택지를 계산하고, 조건에 맞는 모든 접수의 서류 양식을 계산한 뒤 `slice()`로 20건을 선택한다. 검색 입력은 300ms 지연 후 다시 요청하므로 이 비용이 검색 중 반복될 수 있다.

가상 접수 1,000건으로 실제 `list({ page: 1 })`를 실행했을 때 반환은 20건이지만 서류 양식 선택은 1,000회였다. 단, 서류 상태 SQL은 이미 보이는 20건의 ID를 묶어서 조회한다. 여기의 주된 문제는 상태 SQL의 N+1이 아니라 페이지 선택 전에 수행되는 전체 접수 조회/계산이다.

수정 제안:

1. 먼저 DB에서 조건에 맞는 접수 ID 20건과 전체 건수를 얻는다.
2. 해당 ID에 대해서만 답변·첨부 메타데이터·상태를 일괄 조회한다.
3. 필터 선택지는 별도 집계 쿼리로 계산하고, 필요하면 데이터 버전에 따라 캐시한다. 다중 필터의 현재 동작은 유지한다.
4. 서류 열 개수는 해당 조건에 적용되는 양식별 서류 수로 계산한다. 단순히 페이지를 먼저 자르면 페이지마다 열 개수가 달라질 수 있어 기존 의미를 보존해야 한다.
5. 빈번한 검색 요청은 이전 요청 취소/중복 요청 병합을 검토한다. 현재 revision 검사는 오래된 응답의 화면 반영을 막지만 서버 계산은 이미 진행된다.

이를 쉽게 하려면 접수 기본정보 저장 구조를 함께 정리하는 것이 좋다. 현재 `app_subm`은 답변마다 이름·이메일·비밀번호 해시·상태·일시를 반복 저장한다. 기본정보와 검색/정렬 컬럼을 `app_meta` 또는 별도 접수 헤더로 옮기고, 답변 테이블은 `(submission_id, field_key, answer_data)` 중심으로 유지한다. 동적 질문 자체를 없앨 필요는 없다.

접수 일시는 기존 `MIN(created_at)`/`MAX(updated_at)` 의미를 보존해 이관한다. 목록 정렬에는 `(updated_at, id)` 등을 검토하고, 모집 구분은 가능한 한 안정된 ID/코드를 사용한다. 인덱스는 실제 조회 조건과 실행 계획을 확인한 후 결정한다. `%검색어%` 형태의 부분 일치가 일반 인덱스 추가만으로 해결된다고 가정하면 안 된다.

## 5. 첨부파일·수험표의 반복 접수 조회

근거: `server/modules/admit-cards/submission-records.js:13`, `server/modules/applications/service.js:3012`, `3057`, `3622`, `server/modules/applications/archive-jobs.js:92`.

수험표는 수험번호를 200개씩 묶어 접수를 조회하지만, 각 레코드를 만들며 `getApplicantSubmissionPhoto()`를 호출한다. 이 함수는 이미 읽은 접수의 전체 답변을 다시 조회한다. 사진이 없거나 레거시 경로를 탐색하면 추가 조회도 생긴다.

첨부 ZIP도 접수 조회 후 파일 하나마다 `getApplicantSubmissionFile()`이 같은 접수를 다시 조회한다. 예를 들어 접수 N명당 파일 F개가 있으면 파일 조회 경로만 대략 N×F번 추가 접수 조회가 생긴다. 파일을 하나씩 읽는 것은 메모리를 제한하는 좋은 선택이지만, 같은 메타데이터까지 다시 읽을 필요는 없다.

수정 제안:

- DB 조회 함수와 파일 읽기 함수를 분리하고, 이미 조회·검증한 접수/첨부 메타데이터를 파일 읽기에 전달한다.
- 접수는 일정 청크로 조회하고 첨부파일은 제한된 수만 동시에 처리한다.
- 사진 없는 접수는 알려진 상태를 활용해 불필요한 탐색을 줄인다. 기존 사진 저장소 호환성은 회귀 검증한다.
- 클라이언트가 보낸 파일 경로를 그대로 신뢰하지 말고, 서버에서 읽은 저장소 키와 소유권으로 접근한다.

## 6. PDF 작업과 백업의 메모리 누적

근거: `server/modules/admit-cards/admit-card-pdf.js:801`, `883`, `1006`; `server/modules/admit-cards/admit-card-jobs.js:230`, `302`; `server/modules/system/service/backup.js:720`, `789`, `877`.

- 합본 PDF는 전체 대상의 레코드/사진과 렌더링 HTML을 모아 한 번에 출력한다.
- 개별 PDF ZIP은 렌더링 단계에 청크/작업자 재사용이 있지만, 대상 레코드/사진과 ZIP 결과는 메모리에 누적한다.
- 완성된 PDF/ZIP `fileBuffer`는 작업 Map에 보관된다. 작업 단위 동시 생성 제한이 없고, 만료 정리는 작업 생성/조회 시 호출되므로 요청이 끊기면 만료된 Buffer가 즉시 해제되지 않는다.
- 백업은 테이블 전체 조회 → 전체 JSON 생성 → ZIP 등록 → `toBuffer()` 순서다. 데이터 규모가 커질수록 메모리와 직렬화/압축 비용이 커진다.

수정 제안:

- PDF/ZIP 결과를 비공개 임시 파일로 저장하고 다운로드는 스트림으로 제공한다.
- 작업 단위 동시 실행 수·최대 대상 수·전체 임시 저장 용량을 제한하고, 정리 타이머를 요청과 독립적으로 실행한다.
- 레코드/사진도 청크별로 가져와 처리 후 참조를 해제한다. 합본 PDF는 청크 출력 후 합치는 방식의 최대 메모리도 따로 측정한다.
- 백업 테이블은 키 기반 분할 조회나 DB 스트리밍을 사용한다. 백업 포맷 변경 시 이전 ZIP 복원 호환성을 유지한다.
- 백업의 데이터 일관성도 함께 검토한다. 현재 테이블별 풀 조회는 공통 스냅샷을 보장하지 않는다. 동일 읽기 스냅샷과 첨부파일 확정 정책을 설계하되, 장시간 스냅샷이 DB에 주는 영향도 측정한다.

재사용할 좋은 구현이 이미 있다. `archive-jobs.js`는 임시 ZIP 파일, 스트림 다운로드, 한 파일 단위 처리, 계정별 1개/전체 2개 생성 제한과 만료 정리를 구현한다. PDF·백업에도 이 방식을 확장할 수 있다.

## 7. 회원 첨부파일이 세션 조회를 무겁게 함

근거: `server/modules/applications/signup-questions.js:48`, `62`; `server/modules/applications/membership.js:137`, `149`, `190`; `server/http/routes/membership.js`의 session 경로.

가입 파일은 Base64로 `profile_json`에 저장한다. 세션 확인은 `SELECT m.*`로 회원 전체를 읽고 `publicMember()`에서 전체 profile JSON을 파싱한다. 공개 session 응답도 이 profile을 반환한다. 파일 하나가 5MiB이면 Base64 문자열만 약 6.67MiB이므로, 첨부가 있는 회원은 단순 인증 확인에서도 큰 데이터를 읽고 파싱하게 된다. `consent_json`도 `m.*`에 포함된다.

수정 제안:

- 가입 파일도 기존 접수 첨부처럼 비공개 파일 저장소에 두고 DB에는 저장소 키·원본명·크기·MIME 등 메타데이터만 저장한다.
- 세션 확인은 회원 ID·이름·이메일·인증 상태 등 필요한 필드만 조회하고, 프로필/파일은 별도 API에서 필요 시 제공한다.
- 기존 가입 파일은 검증 가능한 배치로 옮기고 파일 쓰기 성공을 확인한 후 DB 참조를 바꾼다. 이전 백업 복원도 함께 수정한다.

## 8. 순차 쓰기와 불필요하게 넓은 잠금

근거: `server/modules/applications/service.js:4263`, `4557`; `server/modules/print-history/service.js:38`; `server/modules/system/service/backup.js:1242`; `server/modules/applications/document-status.js:76`.

- 접수 답변을 문항별 INSERT로 저장한다.
- 서류 저장은 기존 답변을 합쳐 문항별 UPSERT를 수행한다.
- 출력 기록은 대상마다 존재/잠금 SELECT와 INSERT를 반복한다.
- 백업 복원은 모든 행을 하나씩 INSERT한다.
- 서류 상태 한 건을 바꾸면서도 활성화된 전체 서류 파일 질문을 `FOR UPDATE`로 잠근 뒤 JS에서 대상 양식을 고른다. 서로 다른 접수의 상태 수정도 같은 질문 행 잠금에 막힐 수 있다.

수정 제안:

- 답변·상태·출력 로그는 복수 VALUES INSERT/UPSERT로 묶는다. 큰 복원은 행 수뿐 아니라 직렬화 바이트 수와 DB 패킷 크기를 고려해 나눈다.
- 출력 대상 검증/잠금은 ID를 정렬해 묶고, 출력 로그도 일괄 저장한다. 실패 시 전체 롤백 의미는 유지한다.
- 서류 질문 잠금은 요청된 field ID와 적용 양식으로 제한하고, 제출 소유권 잠금은 유지한다.
- 변경되지 않은 서류 답변을 재기록할 필요가 있는지 검토한다. 변경 행만 저장하면 `updated_at`의 의미도 선명해진다.
- 동일 DB 연결에 무제한 Promise.all을 적용하는 방식은 왕복을 일괄 SQL로 줄이는 대안이 아니다.

## 9. 동기 해싱이 접수 경로에도 포함됨

근거: `server/modules/auth/passwords.js:1`, `11`, `34`; `server/modules/applications/service.js:4223`.

관리자 비밀번호 도우미는 `scryptSync()`를 사용한다. 이 도우미가 일반 회원의 원서접수 시에도 임의 비밀번호 해시 생성에 호출된다. 따라서 관리자 로그인만의 문제가 아니다. Node.js 메인 스레드에서 동기 해싱이 진행되는 동안 다른 JS 요청 처리도 지연된다.

회원 서비스는 이미 비동기 `scrypt`를 사용한다(`membership.js:7`, `134`). 같은 방식으로 통일하되 해시 포맷과 검증 규칙은 유지하고, 모든 호출부에 `await`를 반영해야 한다. 비동기 해싱도 작업자 풀을 사용하므로 동시 요청 수를 함께 측정한다. API 특성은 [Node.js crypto 공식 문서](https://nodejs.org/api/crypto.html#cryptoscryptpassword-salt-keylen-options-callback)를 참고한다.

## 10. 내보내기 요청의 전체 데이터 왕복과 요청 버퍼링

근거: `client/features/applications/admin-downloads.js`, `server/http/routes/applications.js`, `server/modules/applications/service.js:812`, `server/http/body.js:1`.

접수 Excel과 사진 ZIP 요청은 브라우저가 갖고 있는 전체 행을 `rows`로 서버에 재전송한다. Excel은 이 데이터를 다시 정규화해 workbook 전체를 메모리에 만든다. 사진 ZIP은 ID·번호·파일명만 쓰는데도 전체 답변을 포함한 행을 보낼 수 있다.

일반 `readJsonBody()`/`readBinaryBody()`는 모든 청크를 모은 뒤 합치며 공통 크기 제한이 없다. 반면 회원 경로에는 별도 30MiB 제한이 이미 있다. 따라서 회원 요청까지 무제한이라고 해석하면 안 된다.

수정 제안:

- 내보내기 요청에는 선택 ID 또는 검색 조건·정렬·선택 범위만 보낸다. 서버가 권한 검증 후 원본 데이터를 조회한다.
- 필터 결과 전체 내보내기와 현재 페이지만 내보내기를 구별해 서버 페이지 처리 전환 후에도 기존 기능을 유지한다.
- 크기가 큰 내보내기는 작업 생성/파일 다운로드 방식으로 바꾸고, workbook 생성도 스트리밍 지원 여부와 서식 요구에 맞춰 설계한다.
- 공통 body reader에 경로별 바이트 제한을 두고, 수신 중 한도를 넘으면 413으로 종료한다. 파일은 장기적으로 별도 업로드나 multipart 스트리밍으로 분리한다.

## 추가 개선 후보

- `summary.js:26`의 `DATE(printed_at) = CURDATE()`는 `printed_at >= CURDATE() AND printed_at < CURDATE() + INTERVAL 1 DAY` 같은 범위 조건으로 표현한 뒤 실제 MySQL/MariaDB 버전에서 실행 계획을 비교한다. 날짜 함수 최적화 가능성은 DB 버전에 따라 다르므로 무조건 전체 스캔이라고 단정하지 않는다.
- 초기화마다 실행되는 사진/파일 마이그레이션(`server/app/services.js:318`, `service.js:3209`, `3275`)은 스키마 버전 기록과 청크/재개 지점을 두면 서버 재시작 비용을 줄일 수 있다. 기존 데이터 호환성 확인 없이 제거하지 않는다.
- 설정·일정·가입 질문은 요청 내 재사용부터 적용한다. 프로세스 캐시는 변경 시 즉시 무효화하고, 여러 서버를 쓰게 되면 버전 전파가 필요하다. 접수 가능 시간 판정은 캐시된 결과가 아니라 현재 시각으로 계산한다.
- 브라우저의 다중 필터/대시보드 반복 순회와 정렬은 서버 페이지 처리/집계 전환 후 남는 비용을 보고 최적화한다. 작은 Map 변환부터 먼저 고치는 것보다 전체 데이터 이동을 줄이는 편이 우선이다.

## 유지할 만한 기존 설계

- DB 연결 풀을 사용하고, 접수/서류/출력 쓰기에 트랜잭션을 적용한다.
- 회원 목록은 이미 서버에서 COUNT와 LIMIT 20을 사용하며 상세 첨부를 목록에서 제외한다(`member-admin.js`).
- 서류 상태는 페이지에 보이는 접수 ID를 묶어서 조회한다.
- 첨부 ZIP의 스트리밍·임시 파일·동시 생성 제한을 다른 다운로드 기능에도 재사용할 수 있다.
- 수험표에는 200개 ID 청크 조회와 PDF ZIP 렌더링 청크/작업자 재사용이 있다. 이 부분을 유지하면서 사진 재조회와 전체 결과 보관을 개선하면 된다.
- 감사 로그 조회는 기본 200건, 최대 500건으로 제한한다(`system/service/audit-log.js`).

## 적용 순서와 검증 기준

1. **접수 안정성:** 번호 카운터/유일성, 트랜잭션 연결 재사용, 파일 실패 복구, 비동기 해싱. 풀 한도보다 많은 동시 접수에서 대기·중복·누락이 없는지 검증한다.
2. **관리자 조회:** bootstrap 3회 조회를 우선 1회로 통합하고 부분 갱신을 적용한다. 이후 접수 헤더·목록/상세 분리·서버 페이지 처리·대시보드 집계를 도입한다.
3. **대량 파일:** 접수 메타데이터 재사용, 파일 기반 결과 보관, 작업 수 제한, Excel/백업/복원 분할 처리를 적용한다.
4. **저장 구조 정리:** 회원 Base64 파일 이관과 기존 백업 호환성을 마무리한다. 실제 대용량 가입 파일 사용이 많다면 이 작업은 앞당긴다.

별도 테스트 DB에서 접수 1천/1만/5만 건, 문항 20/50개, 동시 사용자 1/10/50명 정도를 비교한다. 절대 응답시간 목표는 운영 장비와 실제 업무량을 확인한 후 정한다.

측정 항목은 요청당 SQL 수, DB 연결 대기시간, 요청 p50/p95, 반환 행·바이트 수, 서버 RSS/이벤트 루프 지연, 파일 작업 중 일반 요청 지연이다. 대량 작업은 Node 메모리 외에 PDF 브라우저 프로세스 메모리도 포함한다.

완료 기준 예시:

- 번호 발급 SQL 수가 기존 접수 건수에 비례하지 않는다.
- 동시 접수에서 수험번호 중복이 DB 제약으로 차단되고 정상 재시도가 완료된다.
- 목록 20건 조회가 전체 답변을 애플리케이션 메모리로 가져오지 않는다. COUNT/필터 집계 비용은 별도로 확인한다.
- 사진 교체·출력 기록 후 전체 bootstrap 재요청이 없다.
- 첨부 ZIP에서 같은 접수의 전체 답변을 파일 수만큼 재조회하지 않는다.
- 완료 파일 크기가 커져도 작업 저장소가 Buffer를 계속 보유하지 않으며, 요청이 없어도 만료 파일이 정리된다.
- 가입 파일을 가진 회원도 세션 확인 응답에 파일 본문이 포함되지 않는다.
- 기존 회원가입·접수·서류·수험표·백업 복원 동작이 유지된다.

이번 검토에서 실행한 가상 데이터 검증은 bootstrap 호출 수, 서류 목록 계산 수, 번호 생성 후보 조회 수와 동일 스냅샷 후보 충돌, 단일 연결 풀에서 저장/설정 조회의 추가 연결 대기다. 전체 회귀 테스트와 운영 DB 실행 계획/부하 테스트는 실행하지 않았다.
